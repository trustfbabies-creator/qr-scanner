### Token routing prefix — mandatory

All tokens generated by this second backend must begin with the literal prefix:

`TFB1699-`

Then append a cryptographically strong/random unique suffix generated using `Utilities.getUuid()` (or multiple UUIDs). Example shape only:

Do not use a real person's details in the token.

This prefix lets the shared Vercel API route the QR request to the correct Apps Script backend without changing the existing QR scanner page.

The existing ₹999 backend tokens must retain their existing format, so the existing Vercel route can continue routing non-`TFB1699-` tokens to the original backend.

## 8. Check-in backend contract — match existing scanner

The first ₹999 Apps Script backend already uses this request shape in its `doPost(e)`:

```json
{
  "sharedSecret": "server-side secret",
  "action": "checkin",
  "token": "decoded QR token",
  "pin": "staff PIN"
}
```

Responses use JSON and these status codes (maintain compatible names):
- `SUCCESS`
- `ALREADY_USED`
- `INVALID`
- `NOT_ISSUED`
- `PAYMENT_PENDING`
- `AUTH_FAILED`
- `SETUP_REQUIRED`
- `SYSTEM_ERROR`

Second backend `doPost(e)` must:
1. Parse JSON safely.
2. Compare `sharedSecret` with Script Property `TFB_API_SECRET` using a constant-time comparison if practical (at minimum exact comparison).
3. Require action `checkin`.
4. Call `checkInTicket(data.token, data.pin)`.
5. Return JSON using ContentService.

`doGet(e)` must support `?action=health` and return JSON including service name and backend ID, e.g.:
`{ok:true, service:"TFB Couple Pass ₹1699", backend:"1699", timestamp:"..."}`

Do not build an Apps Script HTML scanner page. Camera and scanner UI remain hosted on Vercel.

### `checkInTicket(token, pin)` rules

- Validate the staff PIN from Script Properties `CHECKIN_PIN`.
- Require a non-empty token starting with `TFB1699-`. Reject all other tokens in this backend.
- Find an exact match in either `QR TOKEN P1` or `QR TOKEN P2` on the second response sheet.
- Determine whether matched token is P1 or P2 and use that person's own:
  - full name
  - email status
  - ticket ID
  - check-in status
  - check-in time
- Require the matching person's email status to equal `SENT`.
- Require the couple order's payment status to equal `CONFIRMED`.
- If email is not SENT, return `NOT_ISSUED`.
- If payment is not CONFIRMED, return `PAYMENT_PENDING`.
- If that particular guest's check-in status is already `CHECKED IN`, return `ALREADY_USED`.
- Otherwise write `CHECKED IN` and that guest's check-in timestamp, then return `SUCCESS` with that guest's name and ticket ID.
- The other guest's check-in state must not be changed.
- Use `LockService` to prevent double check-in races.
- Do not approve based on names, email addresses, ticket IDs or UTR alone; QR token is the credential.

Keep the output JSON shape compatible with the current Vercel scanner UI:
`{ok, code, message, detail?, name, ticketId, checkedAt, testTicket:false}`.
